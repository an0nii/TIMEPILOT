# Отчёт: экспорт и сбор метрик TimePilot

## Стек и архитектура

TimePilot — планировщик задач: Go 1.22, HTTP/REST, встроенный HTML/CSS/JavaScript
frontend и PostgreSQL 16. Приложение и PostgreSQL работают в Namespace `timepilot`
существующего однодового minikube-кластера.

VictoriaMetrics single-node развёртывается в Namespace `monitoring` официальным
Helm-чартом `vm/victoria-metrics-single`, версия `0.29.0`, Helm release `vm-single`.
Версия VictoriaMetrics — `v1.134.0`, хранение — PVC 2 GiB, retention — 7 дней.
Все параметры зафиксированы в `monitoring/victoria-metrics-values.yaml`.

Используется pull-модель: встроенный scraper VictoriaMetrics каждые 10 секунд
опрашивает приложение и postgres-exporter. Отдельные Prometheus, vmagent, operator
и Grafana для этого задания не требуются.

```text
TimePilot :9090/metrics ──┐
                        ├── VictoriaMetrics :8428 ── PVC
Postgres exporter :9187 ─┘          │
                        Kubernetes Pod discovery
```

## Экспорт runtime-метрик

В приложение встроена официальная библиотека `github.com/prometheus/client_golang`
версии `v1.20.5`. Зарегистрированы стандартные Go collector и process collector.
Примеры метрик:

- `go_goroutines` — число goroutine;
- `go_memstats_alloc_bytes` — объём выделенной памяти;
- `go_gc_duration_seconds` — статистика времени GC;
- `process_cpu_seconds_total` — потреблённое CPU-время;
- `process_resident_memory_bytes` — RSS процесса.

Отдельный HTTP-сервер приложения предоставляет `/metrics` на порту 9090 без
авторизации. `promhttp.HandlerFor` с `EnableOpenMetrics: true` поддерживает OpenMetrics
1.0 по заголовку `Accept`, возвращая соответствующий Content-Type и `# EOF`.
Также поддерживается Prometheus text format для совместимости со scraper.

Основной HTTP Service публикует только порт 8080. Порт метрик не публикуется через
NodePort/Ingress и доступен по IP Pod внутри кластера. Локальный просмотр выполняется
административным `kubectl port-forward`. При запуске Go вне контейнера `METRICS_ADDR`
по умолчанию равен `127.0.0.1:9090`; в Kubernetes — `:9090` через ConfigMap.

## Бизнес-метрики

Каждая бизнес-метрика имеет тип Counter, единица измерения — успешные операции.
Все четыре серии существуют с нулевым значением сразу после запуска.

| Метрика | Что считает | Момент увеличения |
|---|---|---|
| `timepilot_tasks_created_total` | Успешное создание задач | После успешного `store.Create`, перед HTTP 201 |
| `timepilot_tasks_viewed_total` | Успешное чтение одной задачи | После успешного `store.Get`, перед HTTP 200 |
| `timepilot_tasks_updated_total` | Успешное редактирование задач | После успешного `store.Update`, перед HTTP 200 |
| `timepilot_tasks_deleted_total` | Успешное удаление задач | После успешного `store.Delete`, перед HTTP 204 |

Повторное успешное чтение или редактирование увеличивает соответствующий счётчик.
Получение списка задач, health checks, невалидный ввод, отсутствующая задача и ошибки
БД не увеличивают эти счётчики. Это количество операций, а не текущее количество
объектов в PostgreSQL. В метках нет ID/названий задач, поэтому количество серий ограничено.

Счётчики принадлежат процессу и сбрасываются при его перезапуске. VictoriaMetrics
сохраняет историю; `rate()` и `increase()` учитывают сбросы. Для нескольких реплик:

```promql
sum(increase(timepilot_tasks_created_total[5m]))
```

Событие учитывается после подтверждения операции БД. Учебные счётчики не являются
транзакционным аудитом: при падении между commit и следующим scraping событие может
не попасть в TSDB.

## Экспорт PostgreSQL

В StatefulSet `postgres` добавлен sidecar
`prometheuscommunity/postgres-exporter:v0.18.1`. Он обращается к PostgreSQL
по `127.0.0.1:5432`: контейнеры Pod используют общее сетевое пространство.
Параметры доступа берутся из существующего Kubernetes Secret `timepilot-secrets`.
Для учебного окружения используется имеющаяся учётная запись БД.

Exporter отдаёт `/metrics` на порту 9187. Проверяются не только его доступность
(`up=1`), но и подключение к БД (`pg_up=1`) и реальные метрики PostgreSQL, например
`pg_stat_database_xact_commit` и `pg_stat_database_numbackends`.

## Service discovery

В `spec.template.metadata.annotations` Deployment приложения и StatefulSet PostgreSQL
добавлены `prometheus.io/scrape: "true"`, `prometheus.io/path: "/metrics"` и
`prometheus.io/port` (`9090` / `9187`).

Helm включает встроенный scraper и создаёт ServiceAccount/RBAC. Конфигурация
`kubernetes_sd_configs: role: pod` обнаруживает Pod в Namespace `timepilot`.
Relabeling оставляет только аннотированные Pod в фазе Running, исключает init-контейнеры
и сохраняет только контейнерный порт, совпадающий с аннотацией. Это исключает дубли
при нескольких портах в Pod. IP-адреса не прописаны статически.

К сериям добавляются `namespace`, `pod`, `container`, `job` и автоматически `instance`.
Названия job: `timepilot-web` и `timepilot-database`. При масштабировании и смене IP
новые Pod обнаруживаются автоматически.

## Проверка и демонстрация

```bash
kubectl get pods -n monitoring
kubectl get svc -n monitoring
kubectl get pods -n timepilot
kubectl port-forward -n monitoring service/victoria-metrics 8428:8428
```

В другом Terminal:

```bash
curl -fsS http://localhost:8428/api/v1/label/__name__/values | jq
curl -fsSG http://localhost:8428/api/v1/query --data-urlencode 'query=up' | jq
curl -fsSG http://localhost:8428/api/v1/query --data-urlencode 'query=go_goroutines{job="timepilot-web"}' | jq
curl -fsSG http://localhost:8428/api/v1/query --data-urlencode 'query=pg_up' | jq
curl -fsSG http://localhost:8428/api/v1/query --data-urlencode 'query=pg_stat_database_xact_commit' | jq
curl -fsSG http://localhost:8428/api/v1/query --data-urlencode 'query={__name__=~"timepilot_tasks_.*_total"}' | jq
```

Страница `http://localhost:8428/targets` показывает обнаруженные таргеты и статус
сбора. `monitoring/demo.sh` создаёт, читает, обновляет и удаляет тестовую задачу;
после scraping `monitoring/check.sh` проверяет наличие всех групп метрик
в VictoriaMetrics. Из-за стандартной задержки видимости новых точек в 30 секунд
результат CRUD проверяется примерно через 45 секунд; при первоначальном discovery
скрипт ожидает данные до 90 секунд. Сценарий видео находится в `monitoring/СКРИНКАСТ.md`.

### Результат проверки 25 октября 2026 года

- Helm release `vm-single`: `deployed`; VictoriaMetrics `1/1 Running`, PVC `Bound`.
- TimePilot: `1/1 Running`; PostgreSQL вместе с exporter: `2/2 Running`.
- Обе группы таргетов: `up=1`; соединение exporter с PostgreSQL: `pg_up=1`.
- В TSDB присутствуют Go runtime-метрики и `pg_stat_database_xact_commit`.
- После одного запуска demo все четыре бизнес-счётчика имели значение `1`.
- При временном масштабировании до двух реплик VictoriaMetrics автоматически
  обнаружила обе реплики приложения, обе имели успешный scraping. После проверки
  число реплик возвращено к одному.
- `go test -race ./...` и `go vet ./...` проходят; тест метрик проверяет корректный
  OpenMetrics-ответ и отсутствие увеличения счётчиков на неуспешных операциях.

Для сдачи видео с демонстрацией добавляется в архив как `screencast.mov` или
`screencast.mp4`. Скрипт упаковки требует существующий видеофайл и помещает этот
отчёт в корень архива.
