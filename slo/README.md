# TimePilot: SLI, SLO, SLA и HTTP-пробер

Используется **RBSLO**: доля успешных операций среди учитываемых попыток.
Три счётчика из предыдущего задания — создание, чтение и изменение задач —
сохранены как числители трёх SLI. Добавлен знаменатель попыток и отдельный пробер.
Фильтр `sli_version="1"` исключает старые успехи, для которых ещё не было знаменателя.

- SLO каждой операции: **99.9% за скользящие 30 дней**.
- Общий показатель со стороны пробера: корректные ответы за не более 2 секунд /
  все запланированные им проверки; его SLO также 99.9% за 30 дней.
- Учебный SLA основных операций: **не менее 99% за 30 дней**, по показателю пробера.
- На демонстрационных графиках используется окно **2 минуты**. Пороги остаются теми
  же, но это иллюстрация, а не заключение о месячном выполнении SLA.

Полные определения, формулы, исключения и модель компенсаций: [Отчёт.md](Отчёт.md).

## Запуск

Из корня проекта:

```bash
minikube start
./scripts/minikube-build.sh
./scripts/minikube-deploy.sh
./slo/deploy.sh
```

Скрипт включает `SLO_DEMO_ENABLED=true` в Deployment приложения, перезапускает его
после пересборки образа, устанавливает retention VictoriaMetrics 31 день и запускает
`timepilot-prober`. Пробер использует тот же образ и команду `probe`. Service discovery
из прошлого задания автоматически добавляет его как `job="timepilot-prober"`.
Данные БД и TSDB не удаляются.

Отдельные Terminal, оставленные открытыми:

```bash
kubectl port-forward -n monitoring service/victoria-metrics 8428:8428
```

```bash
kubectl port-forward -n timepilot deployment/timepilot 9090:9090
```

Для просмотра UI приложения, если нужен:

```bash
kubectl port-forward -n timepilot service/timepilot 8080:8080
```

После первоначального старта дайте проберу примерно 150 секунд здоровой работы:
так заполнится демонстрационное двухминутное окно с учётом задержки запросов TSDB.

```bash
./slo/mode.sh healthy
./slo/check.sh
```

Пока окно ещё заполняется, check может не найти данные. Подождите и повторите.
Ожидаемые проценты в здоровом режиме — около 100.

## Открытие графиков

```bash
python3 slo/graphs.py
```

Скрипт напечатает готовые ссылки в **vmui VictoriaMetrics**, с диапазоном просмотра
15 минут, шагом 10 секунд и подписанными линиями. Главные графики:

1. `business_sli` — три SLI операций и горизонтальная цель SLO 99.9%.
2. `probe_sla` — доступность по проберу и пороги SLO 99.9% / SLA 99%.
3. `compliance` — достижение порогов на двухминутном окне: 1 — да, 0 — нет.

Дополнительные: `raw_metrics`, `demo_mode`, `probe_coverage`.
Готовые кликабельные ссылки также находятся в [ГРАФИКИ.md](ГРАФИКИ.md).
Все выражения хранятся в `slo/queries.json`. Отдельный запрос для ручного ввода:

```bash
python3 slo/graphs.py --query business_sli
```

Откройте ссылку в браузере. Если график не обновляется автоматически, нажимайте
`Execute Query` каждые 10–15 секунд или выберите автообновление в интерфейсе.
Диапазон просмотра 15 минут — это ширина графика; `[2m]` в формуле — окно расчёта
каждой точки. Это разные параметры.

## Демонстрация изменения поведения

Перед записью убедитесь, что SLI около 100. Затем запустите:

```bash
./slo/scenario.sh
```

Сценарий переключит приложение в `degraded` на 90 секунд и вернёт в `healthy`.
В течение следующих 150 секунд старые ошибки выйдут из окна и станут видны
восстановившиеся показатели. При прерывании скрипт также пытается вернуть healthy.
Во время записи не закрывайте Terminal с port-forward.

Можно переключать вручную:

```bash
./slo/mode.sh healthy
./slo/mode.sh degraded
./slo/mode.sh down
./slo/mode.sh healthy
```

- `healthy` — запросы выполняются обычным образом.
- `degraded` — каждый второй запрос к трём контролируемым операциям получает 503.
- `down` — все запросы к этим операциям получают 503; это не остановка Pod.

Health checks, `/metrics`, удаление тестовых задач и управление режимом не ломаются.
Это позволяет видеть ошибки бизнеса при `up=1` и вернуть сервис без перезапуска.
Стандартная задержка видимости новых точек VictoriaMetrics — около 30 секунд;
после переключения изменения не появляются на графике мгновенно.

## Завершение демонстрации

Сначала восстановите режим, затем остановите генерацию тестового трафика и отключите
учебный управляющий endpoint:

```bash
./slo/mode.sh healthy
kubectl scale deployment/timepilot-prober -n timepilot --replicas=0
kubectl set env deployment/timepilot -n timepilot SLO_DEMO_ENABLED-
kubectl rollout status deployment/timepilot -n timepilot --timeout=180s
```

При штатной остановке пробер пытается удалить свою оставшуюся тестовую задачу.
После перезапуска приложения port-forward к 9090 может потребоваться запустить снова.
В обычной конфигурации `/demo/mode` отсутствует, а не просто защищён скрытой ссылкой.

## Диагностика

```bash
kubectl get pods -n timepilot
kubectl logs -n timepilot deployment/timepilot-prober --tail=30
kubectl get pods -n monitoring
```

Откройте <http://127.0.0.1:8428/targets>: ожидаются `timepilot-web`,
`timepilot-database`, `timepilot-prober` со статусом UP. `up` проверяет scrape,
а не успешность бизнес-операций. Недоступный пробер или отсутствие попыток —
отсутствие наблюдений, а не автоматически 100% доступности.
