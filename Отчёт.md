# Отчёт о проекте TimePilot

## 1. Доменная область

TimePilot — веб-приложение для управления задачами и планирования времени. Пользователь может создать задачу, посмотреть список или отдельную задачу, изменить описание и статус, удалить задачу. Опциональный AI-планировщик получает текущий список задач, цель пользователя и доступное время, после чего предлагает последовательность рабочих блоков и перерывов.

Пользователь работает с веб-страницей, frontend обращается к backend по HTTP/1.1 REST API, а backend сохраняет задачи в PostgreSQL. Токен AI-провайдера доступен только backend-процессу.

## 2. Стек реализации

- backend: Go 1.22, стандартная библиотека `net/http`;
- доступ к БД: `pgx/v5`;
- frontend: HTML5, CSS и JavaScript без фреймворков;
- СУБД: PostgreSQL 16;
- AI-интеграции: OpenAI Responses API, Anthropic Messages API, Gemini Generate Content API;
- инфраструктура локального запуска: Docker и Docker Compose;
- формат API: JSON поверх HTTP/1.1;
- тесты: стандартный пакет Go `testing`.

Приложение компилируется в один статический бинарный файл, frontend встроен в него, отдельный Node.js-процесс не нужен. AI-интеграция не требует SDK провайдеров и изолирована за интерфейсом `planner.Planner`.

## 3. Основные сущности

Основная хранимая сущность — **Task (задача)**:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | уникальный идентификатор |
| `title` | text | название длиной 1–200 символов |
| `description` | text | подробное описание |
| `status` | text | `todo`, `in_progress` или `done` |
| `created_at` | timestamptz | время создания |
| `updated_at` | timestamptz | время последнего изменения |

Реализованы все CRUD-операции: `POST` создаёт задачу, `GET` читает, `PUT` обновляет, `DELETE` удаляет. Ограничения данных проверяются приложением и PostgreSQL.

**PlanningRequest** — входная модель без постоянного хранения: цель, доступное количество минут и текущие задачи. **PlanningResult** содержит текст плана, имя провайдера и модель. Токен никогда не входит в доменные модели и HTTP-ответы.

## 4. Соответствие методологии Twelve-Factor App

### I. Кодовая база (Codebase)

Код frontend, backend, миграции и описание инфраструктуры находятся в одном Git-репозитории. Из одной кодовой базы можно получить локальное, тестовое, staging- и production-развёртывания. Их различия задаются конфигурацией, а не отдельными вариантами кода.

### II. Зависимости (Dependencies)

Go-зависимости явно объявлены в `go.mod`, а точные версии и контрольные суммы фиксируются в `go.sum`. Базовые образы объявлены с версиями и неизменяемыми digest в `Dockerfile` и `compose.yaml`. Multi-stage сборка изолирует приложение от пакетов хостовой системы; runtime-образ не требует установленного Go или глобальных библиотек.

### III. Конфигурация (Config)

Конфигурация читается из переменных окружения: `DATABASE_URL`, `PORT`, HTTP-таймауты, `AI_PROVIDER`, `AI_MODEL`, `AI_API_KEY` и `AI_BASE_URL`. Поддерживаются также нативные имена ключей провайдеров. В исходном коде нет паролей или токенов. `.env.example` содержит пустые значения секретов, а настоящий `.env` исключён из Git. В production секреты должны передаваться платформой или secret manager.

### IV. Сторонние сервисы (Backing services)

PostgreSQL и AI API рассматриваются как подключаемые ресурсы. Адрес БД заменяется через `DATABASE_URL`, а AI-провайдер — через `AI_PROVIDER`, `AI_MODEL`, ключ и при необходимости `AI_BASE_URL`. Для перехода между OpenAI, Anthropic и Gemini не нужно менять обработчики HTTP или пересобирать frontend. При отключённом AI основная работа с задачами сохраняется.

### V. Сборка, релиз, запуск (Build, release, run)

Стадии разделены:

1. **Build:** `docker build` компилирует код и создаёт неизменяемый образ; аргумент `VERSION` связывается с Git commit или tag.
2. **Release:** готовый образ объединяется с конфигурацией окружения и секретами.
3. **Run:** образ `timepilot:${VERSION}` запускается командами `server` или `migrate`, исходный код при этом не изменяется. Оба процесса в Compose явно ссылаются на один тег образа.

Для отката запускается образ с предыдущим неизменяемым тегом. В registry следует использовать Git SHA или digest.

### VI. Процессы (Processes)

HTTP-процесс не хранит пользовательское состояние в памяти или локальных файлах. Задачи находятся в PostgreSQL, а frontend встроен в неизменяемый бинарный файл. Сгенерированный план возвращается в ответе и не создаёт неявную локальную сессию. Контейнер можно удалить, перезапустить или перенести на другую машину без потери задач.

### VII. Привязка портов (Port binding)

Приложение содержит собственный HTTP-сервер и экспортирует сервис через порт из переменной `PORT` (локальное значение — `8080`). Apache, Nginx или внешний application server для запуска не требуется. Reverse proxy при необходимости добавляется отдельным компонентом.

### VIII. Параллелизм (Concurrency)

Каждый экземпляр `server` — независимый stateless-процесс. Несколько одинаковых экземпляров могут работать за балансировщиком и использовать общую PostgreSQL без sticky sessions. Одноразовый тип процесса `migrate` отделён от web-процесса. Go обслуживает HTTP-запросы конкурентно внутри каждого экземпляра.

В Compose опубликован порт одного экземпляра, поэтому локальное масштабирование потребует убрать фиксированный host port или добавить балансировщик; архитектура приложения это допускает.

### IX. Утилизируемость (Disposability)

После проверки соединения с БД приложение сразу принимает запросы. Оно обрабатывает `SIGTERM` и `SIGINT`: прекращает принимать новые соединения, ждёт текущие запросы в пределах `SHUTDOWN_TIMEOUT`, затем закрывает пул БД. AI-вызовы ограничены `AI_TIMEOUT` и контекстом HTTP-запроса. Для оркестратора доступны `/healthz` и `/readyz`; необязательный внешний AI-сервис не влияет на readiness основной функции.

### X. Паритет разработки и production (Dev/prod parity)

В разработке и production используется PostgreSQL и один контейнерный образ приложения. `compose.yaml` поднимает тот же тип сервиса и выполняет те же миграции, что применяются при релизе. SQLite или специальной in-memory БД в рабочем запуске нет. Различаются только значения конфигурации и масштаб.

Unit-тесты HTTP-слоя используют fake-хранилище, а тесты AI-адаптеров — локальный HTTP test server; это быстрые тестовые зависимости, а не отдельный режим приложения. Полный Compose-стек используется для интеграционной проверки PostgreSQL.

### XI. Журналирование (Logs)

Приложение пишет структурированные JSON-логи в `stdout`, не создаёт и не ротирует файлы. Docker, Kubernetes или внешняя система может собирать и хранить этот поток. Логируются запуск, завершение, HTTP-метод, путь, статус, длительность и ошибки. Тела запросов, пользовательские планы и API-ключи не логируются.

### XII. Административные процессы (Admin processes)

Миграция запускается одноразовым процессом `timepilot migrate`. Она находится в том же репозитории, встроена в тот же бинарный файл, использует тот же `DATABASE_URL` и те же зависимости, что web-процесс. В Compose сервис `migrate` завершается до старта `app`. SQL-операции идемпотентны (`IF NOT EXISTS`), запуск воспроизводим и не требует ручного подключения к серверу.

## 5. Запуск и проверка

```bash
cp .env.example .env
docker compose up --build
```

После запуска:

- веб-интерфейс: <http://localhost:8080>;
- liveness: <http://localhost:8080/healthz>;
- readiness: <http://localhost:8080/readyz>;
- список задач: <http://localhost:8080/api/v1/tasks>;
- состояние AI: <http://localhost:8080/api/v1/ai/status>.

Автоматические тесты запускаются командой `go test ./...`. Настройка AI и примеры API приведены в `README.md`.
